## Gates against the frozen Study 1, 2 and 3 records

Run on the VPS (Python 3.14.4, numpy 2.5.4, sklearn 1.9.1, shap 0.53.0, single-thread BLAS); the old code ran there from a read-only copy of `CDD-ORAN@0c89106`.

**Study 1 discovery (`data/records/study1_raw/e6p-disc-v4an-pmrt-1/out`, the input of the App C tables).** The new code rebuilt the dev, placebo and slice unit tables from the frozen caches and reran every method of `analysis_v4.json` (B 9999). The declared lists are identical for `v2+by`, corr, granger and granger_by on the placebo set and all 18 slices (19 / 19 each), and for shap_gbdt, int and two-tower on the placebo set and the 8 descriptive slices (9 / 9 each). qacm agrees on 8 of 9: on `s300_1` the stored record has one more edge, `prot_min|own|pv`. Old and new code agree exactly on the VPS for that slice (tau, all scores, all declarations); the edge sits at a near-tie between the PR and ANN predictors (held-out R^2 .3524 vs .3499), so the difference comes from the Kaggle stack. The stored `shap_gbdt` results were produced by the sklearn fallback of `score_shap` (GBDT + permutation importance), not by SHAP: the old code's fallback reproduces the stored dev tau (0.024430621094766805 vs 0.02443062109476682), the SHAP path gives 0.12347201099566928; the gate forced the fallback.

**Study 2 and 3 referees (`data/records/study2_3_decision/runs/{e6p-conf-eval-1,e6p-cs-eval-1}`).** Seeds 187000 and 187001 x 15 Study 2 referee arms and 191100 and 191101 x 11 Study 3 arms, with the frozen `E6P_CONF_MAPS.json` / `E6P_CERTSAFE.json`: 49 of 52 episodes equal the record in every field (outcome, `st_*` counters, `policy_counts`, signature, aliases). In the other three (conf 187001 `B2`, cs 191100 `MG:PMRT`, cs 191101 `CS:qacm@dev`), every arbiter counter is equal and the plant's eMBB-violation count differs by 1 to 5 UE-seconds (`B2` also by the last bit of `energy_j`); the old code on the VPS gives exactly the new values, so the difference comes from the Kaggle stack (Python 3.12.13, numpy 2.4.2).
